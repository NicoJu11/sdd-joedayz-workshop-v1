El patrón template

Un ejemplar de calidad. Todo lo que viene después cuesta casi nada.

El proceso
1
Sonnet construye la primera implementación ejemplar, con manejo de errores y tests completos
2
Haiku replica los N−1 restantes siguiendo el template. La calidad es idéntica.
3
12× de reducción de costo. Sin pérdida de calidad. El template hace el trabajo.
Sirve para
  • Múltiples parsers / validators / exporters
  • Generación de tests (seguir el patrón de test)
  • Endpoints API con estructura similar
  • Páginas de documentación
  • Operaciones CRUD entre entidades

El árbol de decisión

Tres preguntas. Cubren el 95% de los casos. Hazlas en orden.

¿Es una decisión arquitectónica crítica o un algoritmo novedoso?
SÍ → Opus. Arquitectura, compresión novedosa, lógica crítica de seguridad, refactoring de alto riesgo.
¿Requiere razonamiento complejo o resolver un problema único?
SÍ → Sonnet. Features nuevas, debugging de race conditions, integración de sistemas, primera instancia de un patrón.
¿Está siguiendo un patrón ya establecido en el codebase?
SÍ → Haiku. Tests para código existente, componentes repetitivos, docs estándar, CRUD.
Ninguna de las anteriores → Sonnet (es un patrón nuevo que aún no existe)

Dependencia de contexto: Haiku necesita un CLAUDE.md + skills fuertes para seguir patrones con fiabilidad. El Pilar 2 no funciona sin el Pilar 1.

La nota de dependencia de contexto al final es importante. Haiku solo es fiable para seguir patrones si hiciste bien el Pilar 1. Sin CLAUDE.md y skills, Haiku genera código genérico que no sigue tus convenciones. Contexto fuerte hace a Haiku confiable para tareas de Nivel 1.

El contexto habilita la delegación

Haiku sin contexto
  • Genera código genérico
  • No sigue tus patrones
  • Comete errores evitables
  • No se puede confiar para Nivel 1
Haiku con contexto fuerte
  • Sigue patrones documentados con precisión
  • Usa la arquitectura correcta
  • Evita anti-patrones conocidos
  • Fiable para el 60-70% de las tareas
